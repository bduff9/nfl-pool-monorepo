# Native animation opportunities: full scan

Date: 2026-10-14. Branch: `native-screen-transitions`. Read-only scan of `apps/web` (Next 16.4, React 19.3 `<ViewTransition>`, `cacheComponents: true`, `partialPrefetching: true`) and `packages/ui`. Everything here can be built with CSS and `<ViewTransition>` (VT). No new dependency.

Line numbers are from the tree at scan time. Another agent was hoisting `PageTransition` in page files during the scan, so page line numbers may be off by a few lines.

## Summary

The animation layer covers route slides (`PageTransition` + `navDepth`), week slides (`WeekTransition`), sidebar tab fades (`nav-fade`), and the dashboard-to-detail morphs (pie, progress bars, titles). The main gaps:

1. **Scoreboard card to game detail header morph is missing** (the user's complaint). The game page also uses the wrong skeleton: the 16-card scoreboard list (`scoreboard/game/[eventId]/page.tsx:15,52`). So the first thing a user sees after tapping a game is a list of fake games. Section 3 covers this in detail.
2. **Skeleton to content swaps are instant on every page.** `PageTransition` sits outside each page's `Suspense`, so the skeleton slides in, but the real content then appears with no transition. Only the dashboard sections, the scoreboard list, and two rankings tables use `Crossfade`.
3. **Taps give no feedback.** `-webkit-tap-highlight-color: transparent` is set (`globals.css:132`) and no `:active` styles exist anywhere. The only signal is the pending dim from `WeekLink`, which waits for the navigation to start.
4. **Live data has no motion.** Score, possession, win probability, and new scoring plays all swap in place every 5 s. For iOS users following games on Sundays, this is where motion would add the most.
5. **Some programmatic navigations and pages are missing transitions.** Submit picks, login, registration, quick pick and forgot password all call `router.push` without transition types. Auth, quick-pick, error and 404 pages have no `PageTransition`. Head-to-head uses a plain GET `<form>`, which reloads the whole document.
6. **The pick and survivor screens could use VT shared names.** Point chips could fly between the bank and the slots, and the survivor week badge could hop between teams. Both already update inside `startTransition`/`useOptimistic`, so VT would fire on them.

## 2. Implementation constraints that apply to every VT item

- **Pairing needs both snapshots in one transition.** With `cacheComponents` + `partialPrefetching`, a navigation commits the page shell (the in-page `Suspense` fallback) first. A named element only morphs if the **fallback** carries the same name. The dashboard already does this with `DashboardLoader` (`WeeklyDashboard/DashboardLoader.tsx:44-56`), and every new destination needs the same treatment.
- **`SharedElement` must keep `default="none"` + explicit `share`** (`ViewTransitions/SharedElement.tsx:12-16`), or the pair silently stops morphing. Week types are pinned to `none` there, so a week change slides rather than morphs. Per-game names follow the same rule.
- **Names must be unique per snapshot** and valid CSS idents (start with a letter, e.g. `game-401671234`). React applies names only while a transition runs, so they create no permanent stacking contexts. The static names `persistent-nav`, `offline-banner` and `app-toaster` are the exceptions; see the comment at `layout.tsx:159`.
- **VTs fire only for transitions.** `router.push`/`Link`, `router.refresh` (used by live polling, pull-to-refresh, foreground refresh, `AppSidebar.client.tsx:48,57`, `AdminGameRow.tsx:48`), `startTransition`, `useOptimistic` setters inside transitions, and Suspense reveals all qualify. Plain `setState` (e.g. `setSelectedGame`, `setIsModalOpen`) does not.
- **Frequent refreshes start document-level VTs.** The scoreboard and game page poll every 5 s. Every named or keyed VT that changes produces a view transition, and `::view-transition { pointer-events: none }` (`globals.css:312`) keeps taps working, but named participants are not hit-testable while it runs. Keep refresh-driven animations under 300 ms.
- **Reduced motion** is handled globally (`globals.css:381-389`). Any new CSS-only animation (`@starting-style`, `:active`, transitions) needs its own `prefers-reduced-motion` guard.

## 3. Deep dive: scoreboard card to game detail header

### 3.1 What exists today

**Only name a card when `game.espnEventId` is set.** That matches exactly the cards that have a link (Final via `GameDetailsLink`, live via `LiveGameStrip`). ### 3.4 Data and Suspense timing (why the skeleton must carry the names)

- Both links use `prefetch={false}`. With `cacheComponents`, the game route's shell is `PageTransition > Suspense fallback` (the page component is synchronous). The navigation commits that shell first, then streams `GamePageBody` after `getLiveGameSummary` resolves. The first transition is therefore **old scoreboard to game fallback**. If the fallback has no `game-${eventId}` element, the card has no partner, and the old card just slides out with the page.
- So the game page needs its own `GameDetailSkeleton` (O2) with:
  - the back link placeholder (same `py-2.5` height),
  - a header box with **identical geometry** to `GameHeader` (`mb-5 flex flex-col gap-2 border bg-muted p-3`, two 44 px rows + status line), wrapped in `SharedElement name={\`game-${eventId}\`}`, with 44 px logo and score placeholders carrying the `-logo`/`-score` names,
  - drive, chart and plays placeholders below.
- **Getting `eventId` into the fallback.** `params` is a Promise and the page is synchronous. Options:
  - **A (recommended): a small client `GameHeaderSkeleton` that calls `useParams()`.** Per `next/dist/docs/01-app/03-api-reference/04-functions/use-params.md` ("Cache Components"), `useParams` **suspends during prerender** for a dynamic param without `generateStaticParams`, so it must sit inside its own `<Suspense fallback={<unnamed header skeleton/>}>` or the build fails. On a client navigation the router already knows the params, so it should resolve synchronously and the named skeleton should be in the first commit. **Verify this in a production build.**
  - **B (fallback if A still shows the unnamed skeleton on the client): one fixed "hero" name.** The skeleton and the real header use `game-hero`. On the scoreboard, only the tapped card gets `game-hero`, set by `flushSync` in the link's `onClick` before `Link` starts its navigation transition. No params are needed, but you have to manage clearing the name. The back-morph only works if the scoreboard state survives.
  - **C (optional enhancement): logos in the skeleton.** Add the team short names to the link (`&home=KC&away=BUF`) and render real `TeamLogo`s in the skeleton. The logo files are already cached from the card, so the morph shows real logos instead of grey circles before the data lands. This changes the URL shape, and `useSearchParams` has the same prerender-suspension rule as `useParams`.
- **Second phase, the reveal.** When `GamePageBody` resolves, the skeleton header (exiting fallback) and the real header (entering content) share names, so React pairs them as a `share` and morphs in place. The geometry is identical, so this reads as a crossfade of content. The rest of the body should use the O3 reveal (fade + slide up).
- **Prefetch.** Consider removing `prefetch={false}` (partial prefetch fetches only the static shell, which is cheap) so the skeleton, and therefore the morph, commits immediately on tap instead of after a server round trip. Today the only feedback during that wait is the `a:has(> [data-link-pending])` dim (`globals.css:397-400`).

### 3.5 Back navigation (game page to scoreboard)

- "« Back to Scoreboard" (`LiveGameDetail.tsx:94`) resolves `nav-back`. For the header to morph back into its card, the scoreboard's first commit must contain the real cards. The scoreboard fallback (`app/scoreboard/loading.tsx:52-72`) has 16 anonymous `GameLoader`s, so a fresh render cannot pair.
- Next 16 keeps visited routes mounted but hidden (the comment at `usePickActions.tsx:71-72` relies on this). If the back link reuses the hidden `/scoreboard?week=N` tree, the cards are present immediately and the morph runs. If the URL differs (e.g. the week param was dropped), the fallback shows and the header just slides out. **Verify in the browser.**
- iOS standalone PWA: browser back (popstate) carries no types, so there is no slide (by design), but `share` morphs still run if both trees are present.
- The card may be scrolled off-screen after return. The morph then flies toward an off-viewport position, which is acceptable. Consider `scroll: false` + `scrollIntoView` of the card only if it looks wrong.

### 3.6 Risks specific to this morph

- **Live refresh collision.** `ScoreboardLiveRefresh` calls `router.refresh()` every 5 s on both pages. A refresh that lands during the 400 ms morph starts a new view transition, which skips the running one (it snaps to the end). It is low-probability and harmless, but visible. Mitigation: skip a poll tick while `document.activeViewTransition` exists.
- **Scroll reset ordering.** The old snapshot captures the card at its scrolled position. Next's scroll-to-top for the new page must happen before the new snapshot, or the header target is wrong. This should be fine because React runs layout work inside the VT update callback, but verify with a card far down the list.
- **Aspect ratio change on md+** (half to full width). The VT image pair keeps aspect ratio and top-aligns by default, so text does not squash, but the old snapshot can overflow the shrinking group briefly. Add `overflow: clip` on `::view-transition-group(game-*)` if needed.
- **Loser greyscale.** The card logo is greyed for the loser, the header logo is not, so the colour crossfades during the morph. That is fine.
- **Desktop vs phone names.** Unlike the dashboard charts (desktop only), the game header is visible on phones, so this morph benefits the main iOS audience.
